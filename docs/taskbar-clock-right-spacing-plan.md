# 任务栏时钟右侧留白优化实施方案

日期：2026-09-20  
项目：liCalendar 松鼠日历  
状态：**终稿（2026-09-20 评审整合）**，已批准实施；代码改动与构建部署随实施步骤进行

## 1 目标与范围

收紧任务栏时钟内容右侧的多余留白，使内容尽量靠近“显示桌面”细条，同时保留细条原有点击区域，保证文字完整、点击准确、退出后系统布局能够恢复。

建议初始目标间距为 **3 DIP**，允许根据实际视觉效果在 **2～4 DIP** 内调整。该数值是设计目标，不是已测得的系统边距。距离应以“显示桌面”区域左边界为基准，而不是屏幕右缘。

本次方案适用于当前生产使用的任务栏 XAML 注入模式。保留现有文字格式、颜色、字号、段落顺序和段间距；两行对齐继续使用已有配置。备用 WebView 覆盖层不是本次主要修改对象。

## 2 已有证据与待核实事项

### 2.1 已确认

- 当前任务栏局部截图中，下行最后一个可见字符距屏幕右缘约 70 个物理像素。此值为截图估计，包含系统右侧区域，不能全部视为可消除空白。
- 两行内容宽度不同，上行末尾到屏幕右缘的距离更大。
- `LayoutHpanelChildren` 已将自建文字段的右边距设为 0；仅减小段间距不能直接消除外层留白。
- `PanelReflow` 分别计算两行宽度，并通过自建横板的 `Width` 控制布局。
- 当前已有 `align1` 与 `align2` 行对齐协议，支持左对齐、居中和右对齐。
- host 的 `DEFAULT_STYLE` 固定下发 `capw=620`，并未按实测容器宽度动态更新。它是行宽预算，不是 620 DIP 的固定占位；`PanelReflow` 通常取内容宽与预算的较小值，并对时间和日期段保留预算让位逻辑。本需求预计不需要联动修改 host 行宽预算，但不能据此排除命中区域同步的必要性。
- 生产管道 `lical-clockbar-b65` 的服务端在 host，客户端连接必须通过 explorer.exe 身份校验（`pipe.rs` `client_is_explorer`），host 命令集为硬编码（advise/props/ping/c1set/c1t/ttc/ttk/ttr/c1free/unadvise），无任意透传入口；开发用 CLI（`clockbar/src/main.rs`）自建的是另一条 b63 管道，对生产 v65 会话无效。**结论：不存在现成的外部诊断通道**，补最小只读触发入口是实施阶段第一项代码改动（tap 侧命令解析已就绪，tap 零改动）。
- tap v65 命令解析仍保留 `c0tree`/`c0meas`/`c0ins`/`c0rm`/`c0add` 全套入口（tap.cpp `CmdC0` 分派）。本任务只启用其中只读的 c0tree/c0meas。
- `is_mouse_in_clock_area` 的命中外扩实测为四边各 2 物理像素（`clock_window.rs`）；钩子快速刷新路径确认为 `refresh_clock_rect_if_in_taskbar`——仅 IsWindow 校验 + GetWindowRect，HWND 找不到即静默放弃本轮刷新，印证 2.2.8 与步骤四的谨慎前提。
- 历史 XAML 诊断日志显示原生时钟外层有多层容器及布局留白，但历史数值不能直接作为当前环境的修改依据。

### 2.2 实施前必须重新测量

1. “显示桌面”区域实际左边界及点击宽度。
2. 两行自建面板、原生时钟内容容器、外层按钮的屏幕边界。
3. 各层 `Margin`、`Padding`、布局槽、实际尺寸及水平对齐方式。
4. 当前任务栏 DPI 与坐标单位，避免混用物理像素和 DIP。
5. 多余空白是否包含通知图标等独立系统元素；独立元素不能作为普通边距压缩。
6. 候选原生属性是否被系统持续回写，以及是否存在裁切或命中测试约束。
7. 原生垂直 `sp` 的 `HorizontalAlignment`、`ActualWidth`、`DesiredSize` 与两行宽度的关系，以及 `sp` 的右边界在外层容器中的位置。
8. 内容宽度变化后，外层时钟按钮槽位是否随之重新测量和收缩；需比较变化前后数据，单次静态快照不能证明传导行为。

## 3 布局策略

### 3.1 分离三类空间

把右侧空白拆成较短一行的对齐留白、时钟容器留白、系统“显示桌面”区域三部分。主要压缩时钟容器留白；两行对齐通过现有配置处理；系统细条原有命中范围予以保留。

### 3.2 目标边界与单位

设显示桌面区域左边界为 `X_desktop`，目标间距为 `G` DIP，当前有效 DPI 为 `D`。换算到屏幕物理坐标后的目标内容右边界为：

```text
G_px = round(G × D / 96)
X_content_target = X_desktop − G_px
```

XAML 属性使用其布局单位，屏幕坐标用于验证边界，不能直接把屏幕偏移量写进 XAML。目标测量以面板布局边界为主，截图中的实际字形边界为辅，字形侧边留白可能导致少量视觉差异。

### 3.3 修改路径选择

优先调整自建面板的布局，使布局占用空间、显示范围与点击范围相符。不能仅靠视觉平移把文字移进系统保留区域，也不能用写死的负边距掩盖尚未定位的空白。

按以下路径定位，不预先假定收缩自建横板就一定缩小时钟槽位或减少右侧间距：

1. **槽位随内容变化，且右侧空白来自自建布局**：先调整自建横板的对齐和确有多余占位的宽度，验证最终右边界。不得把宽度压到实际内容以下来制造贴边效果。
2. **内容变化但槽位不变，或原生 `sp` 留有额外空间**：定位最先阻断布局变化的层级，按“自建横板 → 原生 `sp` → 外层容器”的次序评估最小修改。`sp` 虽是自建面板的宿主，仍属于原生元素，必须满足下述四项条件。
3. **主要差距来自系统 padding、最小宽度或保留区域**：可安全恢复的局部属性调整仍可按四项条件评估；不能安全修改或属于独立系统功能区域的部分予以保留，并记录残余间距。

以上路径以实测空白来源为依据，不能将“槽位会收缩”直接等同于“右侧留白会缩小”。3 DIP 可能需要原生层调整才能达到，工作量应在基线测量后确定；不采用未经当前环境验证的所谓典型 padding 数值估算结果。

如果测量证明主要留白由系统容器提供，应先明确具体元素和属性，再评估最小范围调整。现有实现有避免与系统布局属性争夺控制权的设计经验，因此原生属性修改必须满足以下条件：

- 能可靠定位到本次时钟实例，不影响其他托盘元素。
- 确认该属性没有持续的系统回写；不能通过每秒强制覆盖来维持效果。
- 修改前保存原始属性状态和元素代次，所有退出与恢复路径可以还原。
- 调整后不会触发裁切、布局反馈循环或命中区域错位。

若条件不满足，则保留该层系统布局，采用已验证安全的缩减幅度，并记录剩余间距的来源。不能预先承诺一定达到 3 DIP。

### 3.4 两行对齐

默认保留用户现有两行对齐设置。收紧整体外边距后，较短一行若保持居中或左对齐，右侧仍有自然留白。

如果视觉要求是两行末尾均贴近细条，优先复用已有的两行右对齐设置，无需预先新增对齐协议。但该设置只控制横板在原生垂直 `sp` 内的对齐，能否贴近细条取决于 `sp` 的实际可用宽度及其右边界，必须实测确认。

`sp` 随内容收缩并不意味着两行横板都与它同宽：两行宽度不同时，较短行仍可能通过右对齐靠到较长行的右边界。反之，即使 `sp` 为 Stretch，外层 padding 或固定槽位也可能使其右边界远离细条。行间右边界对齐与整个时钟区贴近细条是两个独立验收项。

## 4 实施步骤

### 步骤一 建立基线

在任务栏稳定后记录截图、元素边界、布局属性、DPI、注入版本和当前对齐配置。截图保持光标远离时钟，避免 tooltip 干扰。测量应至少覆盖正常显示和一次时间文案刷新。

先记录 `git status`、当前提交和相关文件差异。本次评审时已有 `src-tauri/Cargo.toml` 的修改及未跟踪的 `src-tauri/clockbar/tap/sim.exe`；保留其内容，不擅自删除、还原或提交。干净工作树不是测量前提；隔离本任务变更、记录可复现基线即可。基线同时记录运行中 EXE 与 DLL 的版本及哈希，不能把工作区状态当作部署状态。

优先复用现有诊断能力，明确其覆盖范围：

| 工具或函数 | 已有能力 | 需要补充的内容 |
| --- | --- | --- |
| `c0tree` 即 mode 3 | 从原生 Time 向上最多 14 层的类型、尺寸、Margin、对齐；Grid 子项布局槽；部分 TextBlock 样式 | 不包含所有祖先的 Padding、屏幕绝对坐标，也不递归输出自建横板全部几何信息 |
| `FwDump` | FrameworkElement 尺寸、Margin、对齐及部分 Grid 布局槽 | TextBlock 的 Padding 与 TextAlignment 实际由 `DumpTextBlockStyle` 输出，不是通用容器 Padding 诊断 |
| `c0meas` 即 mode 5 | DTIC、容器、原生栈、Time 及栈直接子项的 Actual 和 Desired 尺寸 | 前后多次采样才能判断宽度变化的传导，不自动生成动态对照结论 |

已确认不存在现成外部诊断通道（见 2.1），基线测量分两波执行：

**第一波（零代码，先做）**：记录 git 快照（status/提交/差异）、运行中 EXE 与已部署 DLL 的版本及哈希、任务栏 DPI、显示桌面细条与时钟按钮的屏幕物理矩形（PowerShell 先 `SetProcessDPIAware()`）、时钟缓存矩形（注册表）与任务栏右缘截图。

**第二波（最小只读诊断入口）**：host 侧新增文件触发式诊断——约定文件（`D:/agents_tmp/clockbar-c0.txt`）出现且内容为 `c0tree` 或 `c0meas` 时，经管道向 tap 发送一次只读命令并删除文件。tap 零改动，tap 版本、DLL 名与管道名均不动，仅重构建并部署 host EXE；入口作为常驻只读诊断能力保留（文件门控）。随后以 c0tree+c0meas 建立 XAML 级快照，并通过设置页段开关或自然文案变化（小时位数进位等）做前后对照，验证 2.2.8 的传导行为。若需补充 tap 侧 dump 字段（如容器 Padding），随 tap v66 正式改动一并发版，不为诊断单独升 tap 版本。c0meas 不要求插入探针；c0ins/c0add/c0rm 会改变结构，不作为基线手段。

本任务临时文件应放在 `D:/agents_tmp/clock-right-20260920`；命令和工具的 `TEMP`、`TMP`、`TMPDIR` 同步指向该目录，不使用 C 盘临时目录。

完成条件：能说明多余空白分别由哪一层贡献，并确定第一个最小修改点。

### 步骤二 实现最小布局调整

在 `PanelBuild` 及必要的布局辅助逻辑中实现右侧间距控制。将目标间距集中定义，避免在多个布局分支写入不同数值。继续使用现有行宽预算和数据段溢出处理，不借此更改内容显示优先级。

修改应由面板建立和真正的布局环境变化触发。时间每秒刷新仍走现有文本快路径，不能每秒重建面板或反复修改外层容器。

完成条件：正常文案下间距明显收紧，无裁切、重叠或持续抖动。

### 步骤三 完成生命周期恢复

如果修改了原生属性，保存本地属性状态与必要的有效值，区分原本不存在本地覆盖、普通本地值及绑定等情况。原本无本地覆盖的属性，恢复时使用清除覆盖的方式交回系统样式；不能一律回写旧的有效值而永久遮蔽样式。不能安全保存和恢复的属性不作为修改对象。

将恢复纳入 `PanelFree`、断线自动恢复、关闭注入和卸载路径。按元素代次管理快照，避免把旧树属性恢复到新树。树重建后的旧元素清理要与现有 `PanelOrphan` 语义协调，不能简单丢弃仍需要恢复的引用。

布局目标失效或无法定位时，回到原布局并记录原因。恢复操作应幂等，重复执行不应产生额外布局变化。

完成条件：正常退出、异常断线和树重建后均无边距残留。

### 步骤四 验证动态布局

覆盖时间和日期宽度变化、天气和节日长文案、段显示开关、字号变化、左右及居中对齐、DPI 变化、休眠恢复和 Explorer 重建。若支持多显示器任务栏，分别按所在显示器测量，不能复用主屏幕的坐标或 DPI。

同时验证 host 命中矩形与实际按钮同步。现有完整探测链是 HWND 与 `GetWindowRect` 优先、UIA 兜底，均失败才使用注册表持久化矩形；钩子在任务栏内还有仅基于 HWND 的快速刷新路径。现代任务栏找不到对应 HWND 时，不能假定快速刷新一定成功。

记录变化前后缓存来源、矩形及更新时机，在布局完成后立即测试新旧边界两侧、相邻托盘区域和显示桌面细条。旧缓存可能误拦时钟以外的点击，内容增长时也可能漏接点击，不能视为无害。还应计入 `is_mouse_in_clock_area` 的 2 个物理像素外扩。

优先验证已有刷新机制是否满足要求；若不满足，再在非钩子线程增加必要的刷新或失效处理。不能把 UIA 重操作放入低级鼠标钩子。若证据表明存在不同步，host 命中逻辑应纳入最小修复范围，而不是因 `capw` 固定就排除所有 host 改动。

完成条件：右侧位置随容器正确布局，未引入反复重排或持续震荡。

### 步骤五 构建部署与产物确认

本步骤仅在后续实际实施时执行，本方案交付不触发构建部署。

1. 为修改后的 TAP 分配新版本号；本次分析已复核 v65 为当前占用版本（管道 b65、tap.cpp 与 `mod.rs` 一致），实施分配 **v66**：tap DLL 换名加载，同步 `mod.rs`/`pipe.rs`/`session.rs` 与 DLL 构建版本。
2. 同步 DLL 构建版本、宿主 DLL 路径、管道名称和会话版本常量，避免加载旧模块。
3. 先构建 TAP DLL，再构建宿主。仅涉及后端时使用 `cargo build --release --features tauri/custom-protocol`，必须确认构建成功。
4. 备份当前 EXE 与匹配 DLL，记录构建输出哈希及时间戳。
5. 按项目既定流程结束应用，复制匹配的 EXE 和 DLL 到 `D:/Program Files/li-calendar`，然后重新启动。
6. 对比部署文件与构建输出哈希，确认进程存活、管道握手版本正确、新布局逻辑已执行。不能只凭应用能启动认定部署成功。

若构建失败，停止部署；若新版本发生回归，恢复匹配的旧 EXE 与 DLL，并验证原生布局已恢复。Explorer 重启仅在旧模块或会话无法正常清理时作为必要恢复手段，不作为默认部署动作。

## 6 验收矩阵

| 场景 | 通过标准 |
| --- | --- |
| 默认文案 | 较长一行接近目标间距，文字完整，不侵入显示桌面区域 |
| 两行右对齐 | 两行面板右边界一致，实际字形无明显异常偏移 |
| 布局宽度传导 | 有变化前后测量证明自建横板、原生栈与按钮槽位的关系，剩余间距来源明确 |
| 保留居中或左对齐 | 维持用户选择，较短行允许存在自然留白 |
| 长短文案变化 | 无持续抖动、重叠或额外裁切，原有溢出策略正常 |
| DPI 与显示器变化 | 按当前显示器重新计算，视觉间距合理一致 |
| 休眠恢复与 Explorer 重建 | 新树恢复正确布局，不引用旧元素或叠加修改 |
| 显示桌面细条 | 悬停和点击正常，时钟不抢占命中范围 |
| 布局后立即点击 | 缓存矩形及时对应实际按钮，包含外扩后仍不误拦相邻区域、不漏接时钟点击；覆盖 HWND 不可用的兜底路径 |
| 时钟右键菜单 | 设置和退出可用，tooltip 不遮挡菜单，光标行为不变 |
| 启动后直接右键退出 | 无需其他操作即可退出，系统时钟布局恢复 |
